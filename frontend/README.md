# КиноРек — Frontend

Клиентская часть сервиса персональных рекомендаций фильмов. Работает поверх готового FastAPI-бэкенда.

> **Локально:** `http://localhost:3000` (dev) | **Docker:** `http://localhost:3000` | **API:** `http://localhost:8000/docs`

## Описание

SPA на React + TypeScript + Vite. Пользователь авторизуется, подключает Кинопоиск, настраивает веса рекомендаций, управляет избранным (фильмы, жанры, персоны), собирает коллекции, загружает аватар и ищет контент через единый поиск.

## Технологический стек


| Компонент  | Технология                                     |
| ---------- | ---------------------------------------------- |
| **UI**     | React 18, TypeScript                           |
| **Сборка** | Vite 6                                         |
| **Стили**  | Tailwind CSS 4, shadcn/ui (Radix)              |
| **Тема**   | next-themes (светлая / тёмная)                 |
| **HTTP**   | fetch + JWT (access / refresh)                 |
| **DevOps** | Docker (nginx), переменная `VITE_API_BASE_URL` |




## Быстрый старт



### Разработка (бэкенд в Docker)

```bash
# из корня репозитория
docker compose up -d

cd frontend
npm install
npm run dev
```

Создайте в корне проекта `.env` (если ещё нет) и для фронта укажите:

```env
VITE_API_BASE_URL=http://localhost:8000
```



### Полный стек в Docker

```bash
docker compose up -d --build
```

- Frontend: [http://localhost:3000](http://localhost:3000)  
- API: [http://localhost:8000](http://localhost:8000)  
- MinIO Console: [http://localhost:9001](http://localhost:9001)

### Sprint 3 — Аватар, тема, Docker и обратная связь UI

**Цель.** Превратить уже работающий MVP в сервис, которым приятно пользоваться и который поднимается вместе с бэкендом: персональный аватар, светлая/тёмная тема, тосты вместо «тихих» ошибок, production-сборка в Docker.

**Исходное состояние.** Пользователь умел войти, синхронизировать Кинопоиск и листать рекомендации, но профиль был «без лица», интерфейс только в одной теме, а фронт жил отдельно от `docker compose` API. Ошибки сети часто оставались в `console.error`.

**Как работал.** Сначала согласовал контракт аватара с бэкендом (`POST/DELETE /users/me/avatar`, поле `avatar_url` в `/users/me`). На клиенте нельзя было слепо ставить `Content-Type: application/json` на `FormData` — браузер сам выставляет boundary, иначе MinIO/FastAPI не принимают файл. Тему повесил на `next-themes` и класс `.dark` у `<html>`, чтобы все токены shadcn переключались разом. Docker собрал multi-stage: Node собирает Vite, nginx раздаёт статику и не знает про React. Toasts (`sonner`) подключил с учётом текущей темы, чтобы тёмный режим не давал белую «простыню».

#### [Done] Загрузка и удаление аватара

**Задача.** Пользователь меняет фото профиля из аккаунта, шапка сразу показывает новый аватар.

**Как сделано.**
- Компонент `ProfileAvatar` на `AccountPage`: превью, выбор файла, удаление.
- `userService.uploadAvatar` / `deleteAvatar` → `POST/DELETE /users/me/avatar`.
- После успеха `AuthContext.updateAvatar` обновляет `user.avatar_url` без повторного логина.
- В `Header` тот же URL через `Avatar` / `AvatarFallback` с инициалами, если файла нет.
- Пустые и битые URL обрабатываются: показывается fallback, а не «сломанная картинка».

**Критерии приёмки.**
- [x] Можно загрузить изображение и увидеть его в профиле и в шапке без F5.
- [x] Можно удалить аватар и вернуться к инициалам.
- [x] Ошибка сети/формата показывается тостом, сессия не сбрасывается.

#### [Done] Светлая и тёмная тема

**Задача.** Переключение темы в один клик, состояние не теряется после перезагрузки.

**Как сделано.**
- `ThemeProvider` на `next-themes`, `attribute="class"`, `defaultTheme="system"`.
- `ThemeToggle` в шапке рядом с поиском.
- Проверка, что карточки, диалоги, инпуты и toasts читаемы в обеих темах (контраст бейджей, постеров-заглушек, кнопок).

**Критерии приёмки.**
- [x] Тема переключается без перезагрузки SPA.
- [x] Выбор сохраняется между сессиями.
- [x] Системная тема подхватывается при первом заходе.

#### [Done] Docker-сборка фронтенда

**Задача.** `docker compose up --build` поднимает UI на `:3000` рядом с API.

**Как сделано.**
- `frontend/Dockerfile`: этап `npm ci && npm run build`, этап nginx с `frontend/nginx.conf`.
- Сервис `frontend` в корневом `docker-compose.yml`, сеть общая с backend.
- `VITE_API_BASE_URL` задаётся на этапе сборки; в dev тот же URL из корневого `.env`.

**Критерии приёмки.**
- [x] Образ собирается без ручного копирования `node_modules`.
- [x] Статика отдаётся nginx, SPA не ломает «глубокие» пути за счёт fallback на `index.html`.
- [x] Фронт ходит в API `http://localhost:8000`.

#### [Done] Тосты и человекочитаемые ошибки

**Задача.** Любое значимое действие (синк Кинопоиска, избранное, аватар) даёт понятный фидбек.

**Как сделано.**
- `Toaster` в корне приложения, тема тостов следует за UI.
- Успех / ошибка на ключевых мутациях; сетевые падения не оставляют «кнопку в вечной загрузке».

**Критерии приёмки.**
- [x] Пользователь видит результат действия без открытия DevTools.
- [x] Тосты читаются и в светлой, и в тёмной теме.

**Отчёт по спринту.** Plan vs Fact: **4 / 4**.  
Нюанс интеграции: URL аватара собирает бэкенд (`MINIO_PUBLIC_URL`, обычно `:9000`). Проверил полный контур compose: frontend `:3000`, API `:8000`, MinIO Console `:9001`.  
Задел на Sprint 4: актёры в профиле всё ещё «строки имён», нужно дотянуть их до карточек как у фильмов.

### Sprint 4 — Персоны: поиск, карточки, избранное

**Цель.** Закрыть паритет с модулем Persons на бэкенде: искать актёров и режиссёров, смотреть карточку, добавлять в любимые — с тем же визуальным языком, что у фильмов.

**Исходное состояние.** Поиск умел только фильмы. В профиле любимые актёры если и были, то как текстовый список, без постера и профессий. Бэкенд уже отдавал `/persons/search`, `/persons/{id}`, `/persons/favorite`.

**Как работал.** Сначала нормализовал ответ Кинопоиска (`kinopoiskId` / `personId` / `nameRu`) в единый тип `Person` в `api.ts`, чтобы карточка не знала про легаси-поля. `PersonCard` сверстал 1:1 с `MovieCard` по сетке: `aspect-[2/3]`, `h-full`, `overflow-hidden`, иначе в одном ряду карточки разной высоты ломали сетку. Поиск расширил второй вкладкой, не плодя отдельную страницу. Избранное персон связал и с профилем, и с диалогом деталей, чтобы сердце и корзина не расходились.

#### [Done] PersonCard — карточка персоны

**Задача.** Сетка актёров визуально рифмуется с сеткой фильмов.

**Как сделано.**
- Постер, имя (`name_ru` с запасным `name_en`), компактный режим для поиска.
- Заглушка «ФОТО НЕДОСТУПНО», если URL пустой или `onError` у `<img>`.
- Скрытие внутреннего скроллбара карточки (как у фильмов).

**Критерии приёмки.**
- [x] В поиске и в профиле карточки одного размера и ритма.
- [x] Нет «полоски» скролла справа у самой карточки.

#### [Done] Поиск персон

**Задача.** Из той же модалки поиска находить актёров и режиссёров.

**Как сделано.**
- Вкладка «Персоны» в `SearchDialog` → `GET /persons/search?query=&page=`.
- Клик открывает `PersonDetailsDialog` и закрывает поиск.
- Минимум символов для запроса — как у фильмов, чтобы не долбить API однобуквенными префиксами.

**Критерии приёмки.**
- [x] Поиск персон работает в той же модалке, что и поиск фильмов.
- [x] Пустой результат и лоадер не ломают вёрстку.

#### [Done] Избранные актёры в профиле

**Задача.** Вкладка «Актёры»: поиск, добавление, сетка любимых, удаление.

**Как сделано.**
- GET `/persons/favorite`, POST/DELETE `/persons/favorite/{id}`.
- Подсказки при вводе имени (до трёх карточек), клик добавляет в любимые.
- На карточке в сетке — кнопка удаления с `stopPropagation`, чтобы не открывать детали случайно.

**Критерии приёмки.**
- [x] Добавление и удаление видны без перезагрузки вкладки.
- [x] Уже добавленный актёр не предлагается в подсказках повторно.

#### [Done] PersonDetailsDialog

**Задача.** Детальный просмотр персоны и тоггл избранного.

**Как сделано.**

- Кнопка «В избранное» / «В избранном», скрытый скроллбар диалога — как у фильма.
- Неавторизованному показывается тост с просьбой войти.

**Критерии приёмки.**
- [x] Диалог открывается и из поиска, и из профиля.
- [x] Состояние сердца совпадает со списком на вкладке «Актёры».

**Отчёт по спринту.** Plan vs Fact: **4 / 4**.  
На ревью вёрстки всплыло, что строка профессии с бэка часто дублирует роли («Актёр, Актёр, Режиссёр») и один и тот же текст торчал и под заголовком, и у кнопки избранного. Это ушло в полировку Sprint 5, чтобы не смешивать новую фичу с косметикой.

### Sprint 5 — Коллекции, сессии и полировка UX

**Цель.** Закрыть продуктовую дыру «мои подборки», дать контроль над сессиями (`logout` / `logout-all`) и довести уже существующие списки (избранное, жанры, поиск) до состояния «нажал — сразу видно», без F5 и без ливня запросов на каждую букву.

**Исходное состояние.** Спринты 3–4 дали аватар, тему и персон. Избранное фильмов/жанров формально было, но из‑за `limit=10` на бэке и разделённого состояния «диалог vs вкладка профиля» UI врал, пока не обновишь страницу. Коллекций на клиенте не было. Выход сразу чистил `localStorage`, не отзывая refresh на сервере.

**Как работал.** Спринт шёл в связке с бэкендом коллекций и `POST /auth/logout-all`. Сначала нарисовал IA: отдельный view `collections` в `App` (без React Router — три состояния `catalog | account | collections`), шапка с иконкой библиотеки. Потом клиент `collectionService` строго по OpenAPI: `POST /collections`, `GET /collections/my|public|search|{id}`, PATCH/DELETE, фильмы в подборке. Когда поиск Кинопоиска отдавал id, которого нет в таблице `movies`, бэкенд при добавлении в коллекцию сам подтягивает карточку — на UI убрал тупик «фильм не в каталоге». Параллельно поднял избранное в `App`, чтобы сердце, корзина и вкладки читали один источник правды. Поиск в коллекциях и фильтр «Найти среди своих» посадил на debounce 400 мс с отменой устаревшего результата. В конце — диалог выхода и выравнивание карточек персон с фильмами.

#### [Done] Debounce поиска, чтобы не дёргать API и сетку

**Задача.** Один символ ≠ пачка запросов и не «мигание» списка.

**Как сделано.**
- Поле «Добавить фильм из каталога» только пишет в state; эффект с таймером 400 мс вызывает `/films/search`, cleanup отменяет устаревший ответ.
- «Найти среди своих» фильтрует уже загруженные коллекции по `debouncedSearch`, а не по сырому `search` — инпут живой, сетка перерисовывается после паузы.
- Причина множественных запросов: вызов API прямо из `onChange` без задержки; в dev дополнительно мешал `React.StrictMode` на эффектах.

**Критерии приёмки.**
- [x] При вводе серии букв уходит один запрос после паузы.
- [x] Список своих коллекций не прыгает на каждую букву.

#### [Done] Выход из текущей сессии и со всех устройств

**Задача.** Честный logout по контракту бэкенда (`token_.py`: revoke одного hash vs revoke всех refresh пользователя).

**Как сделано.**
- Клик по иконке выхода открывает диалог, а не сразу чистит storage.
- **Выйти** → `POST /auth/logout` с `{ refresh_token }` (отзыв текущей сессии).
- **Выйти со всех устройств** → `POST /auth/logout-all` (Bearer access, `revoke_all_user_tokens`).
- **Отмена** оставляет пользователя в аккаунте.
- Даже если API ответил ошибкой, локальные токены и профиль всё равно сбрасываются, чтобы UI не прикидывался авторизованным.

**Критерии приёмки.**
- [x] Два явных действия плюс отмена.
- [x] После выхода пользователь видит лендинг, access/refresh в `localStorage` нет.
- [x] «Со всех устройств» бьёт в `/auth/logout-all`, а не только чистит браузер.

#### [Done] Единая структура карточек персон (полировка Sprint 4)

**Задача.** Убрать дубль специальностей и выровнять иерархию с `MovieCard` / `MovieDetailsDialog`.

**Как сделано.**
- `parseProfessions`: нарезка по запятой/точке с запятой, уникальность без учёта регистра.
- Карточка в сетке: постер → имя → подпись (англ. имя или «-») → бейджи профессий (до двух, как жанры у фильма).
- Диалог: заголовок = имя, подзаголовок = англ. имя или «Персона кинематографа», ряд с кнопкой избранного, ниже бейджи **один раз** (не дублировать строку у сердца).

**Критерии приёмки.**
- [x] Одна и та же профессия не повторяется под именем и у кнопки.
- [x] Сетка и диалог раскладывают блоки в том же порядке, что карточки фильмов.

**Отчёт по спринту.** Plan vs Fact: **5 / 5**.  
Интеграционный риск: фильм из `/films/search` мог не существовать в `movies` — это чинилось согласованно с бэкендом (ensure movie при добавлении в коллекцию), на фронте убрали вводящее в заблуждение сообщение.

**Ключевые решения.** Один `api.ts` как фасад REST; избранное и коллекции в состоянии `App`, чтобы диалог и вкладки не расходились; debounce на «живых» полях ввода; Docker + nginx, чтобы UI ехал в том же compose, что API.

**Что сознательно не делал.** Отдельный React Router (трёх view в `App` хватило), E2E на Playwright, курсорную пагинацию (бэкенд даёт `page`/`size`, на клиенте — страницы по 12–100).
